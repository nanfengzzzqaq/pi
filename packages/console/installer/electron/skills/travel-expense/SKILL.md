# 差旅费用报销自动填报（易快报 / 合思）

用户给出飞书审批链接（app.ekuaibao.com，含 accessToken）时使用本技能。
核心原则：**只填表 + 存草稿，绝不点击“提交送审”，绝不删除单据。**

## 一次性附件预检

开始时只做一次完整预检，把本次行程所缺内容合并成一条消息向用户索要，不要边填边反复中断：

1. 报销链接（消息里已有就不再询问）。
2. 关联申请线索（城市、日期或标题；能唯一匹配就不再询问）。
3. 每程铁路电子客票（OFD 或含 OFD/PDF 的 ZIP）及对应查验截图；多天出差再要住宿发票及已有的住宿查验附件（没有住宿查验件时明确按空数组处理）。

附件尚未齐全时，可以先打开页面、关联申请并填写可确定的基础字段；费用明细和上传留到附件齐全后一次完成。仅当申请存在多个同名候选、票据金额冲突或关键必填值无法核实时再停下来问用户。

## 第一步：解析票据附件

用户发来的所有票据附件（.ofd 或 .zip）**集中调用一次 `travel_read_invoices` 解析**，直接得到
车次、原始起止站、归一后的起止城市、日期、席别、票价、乘车人、发票号和每张票对应的上传文件路径。
一个 ZIP 中有多张 OFD 时会分别返回，严禁把两张票的字段或附件混在一起。
不要自己用 bash/powershell 手工解压解析。查验截图（图片）不需要解析，留作上传附件。

## 页面稳定锚点（data-testid）

- 关联申请：`field-expenseLink-select`
- 报销说明输入框：`field-text-u_事由`
- 费用明细“添加”：`field-expenseDetail-add`
- 明细费用类型候选：`template-feeType-item`（按完整可见文字精确选择）
- 明细抽屉保存：`feetype-footer-save`；取消：`feetype-footer-cancel`
- 存为草稿：`flexable-button-edit`
- **提交送审：`flexable-button-submit`——任何情况下都不许点击**
- 其余字段用 browser_snapshot 的 ref 或可见文字定位。

## 标准流程

1. `browser_navigate` 打开用户给的报销链接，`browser_wait` 等出现“差旅费用报销单”。
2. 点击 `field-expenseLink-select` 打开关联申请弹窗：用 `input[placeholder="搜索标题和单号"]` 输入申请标题关键词（如“常州”），在同时包含申请标题和单号的同一父行内选择 radio，再点“确认”。不要按旧 ref 或第几个 radio 猜测。
   - 选择前可点该申请的“详情”查看事由、费用性质、起止日期、城市，记录下来。
   - 关联成功后“申请单中的差旅起止日期”会自动带出；把它作为后续一切日期的依据。
3. 核对自动带出的字段（正常不用动）：所属公司=赛昇信息技术研究院江苏有限公司、提交人=苏爱健、报销日期=当天、申请人部门与费用所属部门=工业信息安全组。
   - 部门若为空：两个字段都按 赛昇信息技术研究院江苏有限公司 → 政策支撑部 → 工业信息安全组 逐级选择，且两处保持一致。
4. 填“报销说明”：写入关联申请的事由（如“常州业务拓展”），输入框 `field-text-u_事由`。
5. “驻地”：点开选择框后直接输入 **江苏省南京**，选择唯一匹配结果。**不要选“市辖区/市区”一类节点。** 输入后失焦并重新读取字段，确认页面没有回退为空。
6. “费用性质”：与关联的出差申请保持一致。先看申请详情里的费用性质（两种：部门费用 / 项目费用），当前值不对就点开下拉切换。
7. “关联项目”、“核销借款”、“是否为多收款人”：一律不处理。
8. “支付信息”：点“请选择支付信息”，选择收款人 **苏爱健**。
9. 生成费用明细计划：调用 `travel_plan_details`，传入申请起止日期、逐程车票（归一城市、乘车日期、席别、金额、乘车人、发票号、`uploadFile`——全部来自第一步解析结果）以及该程唯一对应的 `verificationFiles`；多天出差再传住宿金额、日期、住宿发票 `uploadFile` 和住宿 `verificationFiles`（没有则传空数组）。
   - 每程的电子客票和查验附件、住宿发票必须在生成计划前一次配齐；缺失、文件不存在或交通/住宿之间复用同一文件时工具会直接拒绝，不能靠猜测继续。
   - 当前报销人固定为苏爱健，所有铁路票据的乘车人必须是苏爱健；即使多张票上的其他乘车人彼此一致也必须停止，不能生成计划。
   - 判断规则：当天往返（起止同一天）只有 城市交通费 + 出差补助；多天出差为 城市交通费 + 住宿费 + 出差补助。
10. 逐条添加费用明细：点 `field-expenseDetail-add` → 在“添加明细”抽屉里先选费用类型，再按计划填字段：
    - 费用类型候选均为 `data-testid=template-feeType-item`；城市交通精确选择文字以“差旅-城市间交通费-火车I高铁”开头，住宿和补助分别选择“差旅-住宿费”“差旅-出差补助”。
    - **城市交通费**：先在必填“上传发票”区通过“添加发票”上传计划行里的 `uploadFile`；再填写 placeholder 为“开始日期/结束日期”的日期（两者使用关联申请完整起止日期，不缩成单程乘车日）、标签为“出发城市/到达城市”的城市选择框、标签为“乘坐火车席别”的下拉框，以及 `input[placeholder="请输入报销费用金额"]`。计划行会另存“乘车日期”供核对；每程一条（往返各一条）。
    - **住宿费**：金额与住宿发票一致，起止日期为入住~离店（或与申请一致）；“上传发票”使用该住宿计划行的 `uploadFile`，附件区使用同一行的 `uploadFile` 和非空时的 `verificationFiles`。
    - **出差补助**：补助类型固定选 **其他省份**；起止日期与申请一致；金额由系统按 180 元/天自动核算，不要手改。
    - 每条填完后点 `feetype-footer-save`，回到主表确认明细数增加 1；下一条重新点“添加”并重新 browser_snapshot，不沿用上一条 ref。
11. 定向上传票据：在**每条费用明细自己的附件区**调用 `browser_upload`，用该明细上传入口的 ref/selector 定向上传；页面有多个上传框时绝不省略目标。
    - 每条城市交通费的“上传发票”严格绑定该计划行的 `uploadFile`；该行下方“附件”再定向上传同一计划行的 `uploadFile` 和 `verificationFiles`。不要把往返附件混在同一行，不要复用另一行文件，也不要上传到表单顶部通用附件区。
    - 住宿发票及其查验附件只按住宿计划行绑定到住宿费明细，不能复用任一交通行的文件；出差补助不上传票据。
    - 不要上传临时目录文件，不要把同一 PDF 绑定给多张票；上传后重新读取并核对该行显示的文件名。
12. 持久性复查：每个输入/选择完成后触发失焦，再重新 `browser_snapshot` 读取；确认报销说明等字段没有因页面重渲染被清空。最后确认全部红 *、明细条数、附件文件名与系统核算金额。
13. 点击 **存为草稿**（`flexable-button-edit`）后必须调用 `browser_wait` 等到页面明确出现“保存成功”（或“已存为草稿”），再重新快照核对；单纯点击成功不算保存成功。随后向用户汇报草稿内容与金额；**不得继续点击任何提交按钮**。

- G7575：南京南站 → 常州站，归一城市 南京 → 常州，二等座，72 元，乘车人苏爱健。
- G7018：常州站 → 南京站，归一城市 常州 → 南京，二等座，75 元，乘车人苏爱健。

- 页面最终只保存草稿，不提交、不删除。

## 红线

- 绝不点击 `flexable-button-submit`（提交送审）。
- 绝不点击“删除单据”。
- `travel_plan_details` 的补助固定为 180 元/天，任何用户输入或模型推断都不得覆盖。
- 保存前必须核对关联申请、乘车人固定为苏爱健、发票号无重复、交通和住宿附件无跨行复用、行程日期在申请范围内、每笔金额大于 0。
- 金额与票据不一致、必填项拿不准、申请匹配有歧义时：停下来问用户，不要猜。
- 页面结构变化导致找不到锚点时：browser_snapshot 重新定位；连续失败就如实告知用户卡在哪一步。
- “继续”“接着”“保存草稿”以及 .zip/.ofd/.pdf/.png/.jpg 附件消息都会续载页面交互能力；不要要求用户重复发送固定触发词。
